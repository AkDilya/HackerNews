# ДЗ №6 — Настройка CI/CD и интеграция сервисов

**Проект:** TrendRadar — трекер технологических трендов (Hacker News + Dev.to)
**Роль:** DevOps / безопасность. Автоматизация сборки, интеграции, аудит и мониторинг — выполнены в паре с AI-агентом (Claude Code / OpenCode): агент генерировал конфигурации, а каждое исправление проверялось живым запуском.

---

## 1. CI/CD Пайплайн (GitHub Actions)

Пайплайн описан в **`.github/workflows/deploy.yml`** и состоит из двух параллельных job'ов — под каждую часть системы.

**Триггер:** пайплайн запускается при **пуше в ветку `main`** и на pull request'ы в `main`:

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
```

### Job `backend` — lint & smoke

1. **Установка зависимостей**: Python 3.14 (`actions/setup-python`) → `pip install -r backend/requirements.txt`, `-r collector/requirements.txt` и `flake8`.
2. **Линтинг**: `flake8 backend collector --select=E9,F63,F7,F82` — синтаксические ошибки и «ловушки» (шаблон GitHub для Python); с этим набором CI ловит падения от опечаток, не заваливаясь на стилистике.
3. **Smoke-проверка**: `python -c "import main"` — приложение импортируется целиком (все роутеры, конфиг, CORS), значит сборка не «смертельная».
4. **Деплой на Railway** (`railway up`): выполняется только на пуше в `main` и **только если задан секрет `RAILWAY_TOKEN`** — без настроенного облака шаг вежливо пропускается, чтобы проект оставался запускаемым локально.

### Job `frontend` — install, lint, build

1. **Установка зависимостей**: Node 20 (`actions/setup-node` с кэшем npm по `package-lock.json`) → `npm ci` (воспроизводимая установка строго из lock-файла).
2. **Аудит безопасности**: `npm audit --omit=dev --audit-level=high` — production-зависимости проверяются на известные CVE прямо в пайплайне.
3. **Линтинг**: `npx eslint src` — шаг выполняется, когда в репозитории появится конфиг ESLint (сейчас его нет, поэтому job его пропускает — CI не должен быть красным из-за отсутствующего инструмента).
4. **Сборка**: `npm run build` — production-бандл Vite.
5. **Деплой на Vercel** (`vercel --prod`): аналогично Railway — по секрету `VERCEL_TOKEN` и только на пуш в `main`.

Таким образом, один и тот же пайплайн сегодня работает как **CI** (проверка каждой правки), а после заведения секретов развёртывания превращается в **CD** (автодеплой фронтенда на Vercel, бэкенда — на Railway) без изменения кода.

### Локальное/серверное развертывание: Docker Compose

Вместо «трёх терминалов» весь стек поднимается одной командой — `docker compose up --build`:

| Сервис | Образ | Роль |
|---|---|---|
| `mongo` | `mongo:7` | База `trendradar`, данные в named volume `trendradar_data` |
| `backend` | `backend/Dockerfile` (python:3.14-slim) | FastAPI на `:8000`, env передаётся через compose (`MONGODB_URL=mongodb://mongo:27017`, JWT/GITHUB — из переменных окружения, не из образа) |
| `ollama` | `ollama/ollama` | Локальная LLM (`qwen2.5:0.5b` тянется командой `docker compose exec ollama ollama pull qwen2.5:0.5b`) |
| `collector` | `collector/Dockerfile` (контекст — корень репозитория) | Планировщик: первичный сбор 300 статей + 50 HN/Dev.to каждые 5 минут; `OLLAMA_URL=http://ollama:11434/...` — сервис-имя вместо localhost |
| `frontend` | `frontend/Dockerfile` (multi-stage: Node build → nginx) | Production-бандл Vite, отдаётся nginx на `:5173` с SPA-fallback (`try_files … /index.html`), кэш для `/assets/` |

Особенности, которые пришлось учесть:

- порты сохранены прежними (`8000`, `5173`) — **CORS бэкенда (`localhost:5173`) и захардкоженный `API_BASE_URL` фронтенда работают без изменений кода**;
- в контейнерах сервисы обращаются друг к другу по именам сервисов compose (`mongo`, `ollama`) — поэтому `MONGODB_URL`/`OLLAMA_URL` задаются через `environment`, который приоритетнее `env_file`;
- `.dockerignore` исключает `.env`, `__pycache__`, `node_modules`, `dist` — секреты и мусор не попадают в образы;
- колектор собирается из корня репозитория, потому что он импортирует модули `backend/` через `sys.path` (текущая архитектура: колектор пишет в Mongo напрямую, минуя API);
- если Ollama недоступна, колектор деградирует в keyword-режим — контейнер не падает, а AI-функции просто работают без LLM.

Пайплайн CI при этом не менялся: он собирает и проверяет те же самые исходники, из которых строится compose-стек.

## 2. Интеграция сервисов

### OAuth2 (GitHub)

Вход через GitHub реализован ранее и подробно описан в [ДЗ №5](./hw5_backend_report.md): `GET /api/auth/github` → GitHub authorize → callback обменивает `code` на `access_token`, создаёт/обновляет пользователя (`upsert`) и возвращает фронтенду JWT (`{FRONTEND_URL}/auth/callback?token=…`). Фронтенд хранит токен в `localStorage` и ходит им в защищённые эндпоинты через `authFetch`.

### Аналитика (Яндекс.Метрика)

В `frontend/index.html` подключён счётчик **Яндекс.Метрики**:

- скрипт `mc.yandex.ru/metrika/tag.js` загружается асинхронно (не блокирует рендер);
- включены **`clickmap`** (карта кликов — видно, по каким карточкам и кнопкам реально кликают) и **`trackLinks`** (переходы по внешним ссылкам статей), `accurateTrackBounce` для корректного показателя отказов;
- `webvisor: false` — запись движений мыши отключена из соображений приватности пользователей;
- ID счётчика задаётся один раз при регистрации на `mc.yandex.ru` (в коде — placeholder `00000000`, подставляется перед публикацией);
- есть `<noscript>`-фолбэк с пикселем-счётчиком для браузеров без JS.

Метрика даёт продуктовой аналитике (посещения, глубина, клики) то же, что Health Check даёт эксплуатации — объективную картину «что происходит».

### Мониторинг: Health Check `GET /api/health`

В `backend/main.py` добавлен эндпоинт, который проверяет не только живость процесса, но и доступность MongoDB:

```python
@app.get("/api/health", tags=["monitoring"])
async def health():
    try:
        await client.admin.command("ping")          # ping MongoDB
        return {"status": "ok", "database": "ok"}   # HTTP 200
    except Exception as exc:
        print(f"❌ Health check failed: {exc}")
        return JSONResponse(status_code=503, content={"status": "error", "database": "unavailable"})
```

Проверено вживую: при поднятой Mongo — `200 {"status": "ok", "database": "ok"}`; если БД недоступна — `503` с телом ошибки. Такой контракт удобен для внешних мониторингов (UptimeRobot, Kubernetes liveness/readiness, cloud balancer health probes): 2xx — «можно лить трафик», 5xx — «выводим из ротации».

## 3. Аудит безопасности (Security Audit)

Аудит проводился в три захода: конфигурация, зависимости, код. Все находки и их статус:

| # | Находка | Статус |
|---|---|---|
| 1 | **CORS** | ✅ Исправлено. Строгий список origins — только `http://localhost:5173` (фронтенд), `allow_methods/headers` ограничены нужным; никаких `allow_origins=["*"]` с credentials. |
| 2 | **Секреты** | ✅ Исправлено. `JWT_SECRET`, `GITHUB_CLIENT_ID/SECRET`, `MONGODB_URL` — в `.env` (gitignored), в коде — только `os.getenv` с безопасными дефолтами; в репозитории — шаблон `.env.example` без значений. |
| 3 | **Валидация входящих данных** | ✅ Реализовано через **Pydantic**: тела запросов описаны моделями (`FavoriteRequest` в favorites, `SubscribeRequest` в subscriptions, `SummarizeRequest` в trends) — POST без обязательных полей/с неверными типами получает `422` ещё до бизнес-логики; query-параметры (`limit`, `skip`, `days`) типизированы сигнатурами эндпоинтов и нормируются (`limit` клампится в допустимые границы). |
| 4 | **Зависимости npm** | ⚠️→✅ Частично исправлено. `npm audit --omit=dev`: найдена **1 high** (`follow-redirects`) — закрыта через `npm audit fix` (транзитивная зависимость axios); **2 moderate** в `react-router` (open redirect / constructor injection) — исправление требует мажорного апгрейда до v7, зафиксированы как известный риск с планом миграции. Сборка после фикса проверена (`npm run build` — ok). |
| 5 | **Зависимости pip** | ⚠️→✅ Частично исправлено. `pip-audit`: найдено **9 уязвимостей в 5 пакетах**; **6 закрыты** обновлением (`dnspython 2.9.2`, `pyasn1 0.6.5` ×4, `opentelemetry-api 1.45.2`); остались 3 без опубликованных фиксов — `ecdsa` (транзитивная от `python-jose`) и `python-jose` (стек JWT). Митигировано: HS256-токены с TTL 30 дней, проверка подписи на каждом защищённом эндпоинте; в планах — миграция на активно поддерживаемый `PyJWT`. |
| 6 | **XSS** | ✅ Проверено. React по умолчанию экранирует всё, что попадает в JSX; **`dangerouslySetInnerHTML` / `innerHTML` в коде фронтенда не используются ни разу** (проверено grep по `src/`). HTML-вывод AI-саммари рендерится как текст. |
| 7 | **Доступ к БД** | ✅ Mongo не торчит наружу: привязка к `localhost:27017`, доступ только из бэкенда/коллектора; очистка БД — отдельный админ-эндпоинт под ключом из `.env`. |

Дальнейший контроль: шаги `npm audit` и flake8 уже встроены в CI-пайплайн (раздел 1) — каждая будущая уязвимая зависимость будет найдена на этапе PR, а не после релиза.

## 4. Логирование и обработка ошибок

**Бэкенд (FastAPI).**

- Каждый слой защищён `try/except`:
  - вызовы **внешних API** — обмен кодом OAuth и запрос профиля к GitHub (`httpx`), генерация саммари через **Ollama**: недоступность внешнего сервиса не роняет endpoint, а возвращает аккуратный ответ (`400` для OAuth, fallback «AI временно недоступен» для LLM);
  - операции **MongoDB** — дубликаты предотвращаются уникальными индексами и фильтрацией перед вставкой; ошибки БД логируются, а не выбрасываются пользователю;
  - **health check** — любая ошибка ping конвертируется в `503` с текстом причины в логе.
- Логи пишутся в консоль в структурированном виде: **uvicorn** даёт форматированные access-логи (`"GET /api/health HTTP/1.1" 200 OK`) и traceback'и с полным стеком при падении, прикладные события — маркерами `print` (`✅ База данных и индексы инициализированы`, `❌ Health check failed: …`), по которым легко искать глазами в консоли и слать в агрегатор при переходе на `logging`. *(В планах — переход на стандартный `logging` с JSON-форматтером, см. раздел 5.)*
- Из практики DevOps-отладки: на Windows-консолях с кодировкой cp1251 `print("✅ …")` ронял старт приложения (`UnicodeEncodeError` на эмодзи) — исправлено принудительным `sys.stdout.reconfigure(encoding="utf-8")` в `main.py`. Хорошая иллюстрация, почему логирование нельзя оставлять «просто print'ами» без проверки окружения.

**Фронтенд (React).**

- Все запросы к API обёрнуты в `try/catch` с проверкой `response.ok`: недоступность бэкенда превращается в понятное состояние интерфейса (сообщение об ошибке + Retry), а не в белый экран;
- ошибки разработчика — в `console.error` с контекстом (`Feed error: …`, `Cluster error (AI): …`), что видно в DevTools при отладке;
- пользовательские сценарии деградируют мягко: `401` → подсказка войти, пустой ответ → заглушка «нет данных».

## 5. Планы по улучшению

1. **Telegram-бот для алертинга.** Уже есть всё для интеграции: `/api/health` возвращает 503 при падении БД, ошибки логируются маркерами, колектор работает как долгоживущий процесс. Осталось добавить небольшой watcher (или GitHub Action с cron), который шлёт сообщение в чат при `503` от health или новых записях в лог — уведомление о инциденте придёт в карман, а не будет найдено постфактум.
2. **Миграция `python-jose` → `PyJWT`** — закрытие последних 3 pip-аудит находок (и заодно переход на активно поддерживаемый стек JWT).
3. **Апгрейд `react-router-dom` до v7** — закрытие 2 moderate npm-находок (open redirect в `<Link>`).
4. **Внедрить ESLint в репозиторий** — шаг линтинга в CI уже готов и заработает автоматически; там же — `pip-audit` отдельным шагом backend-job.
5. **Структурные логи (`logging` + JSON)** на бэкенде с корреляцией запросов (request id), чтобы при появлении Telegram-алертов сразу понимать, что именно сломалось.
6. **Вынести `API_BASE_URL` фронтенда в env-переменную** (`VITE_API_URL`) и добавить healthcheck-сервисы в compose с `depends_on: condition: service_healthy` — строгое ожидание готовности Mongo перед стартом бэкенда.

## Вывод

TrendRadar теперь проверяется автоматически: пайплайн GitHub Actions на каждый пуш/PR в `main` ставит зависимости, линтит, аудитит и собирает обе части системы, а при наличии секретов развёртывает их (Vercel/Railway). Развертывание унифицировано Docker Compose — весь стек (Mongo, FastAPI, Ollama, колектор, nginx-фронтенд) поднимается одной командой без правки кода. Сервисы интегрированы: GitHub OAuth (сессии), Яндекс.Метрика (продуктовая аналитика), `/api/health` (эксплуатационный мониторинг с проверкой MongoDB — `{"status": "ok"}` / `503`). Аудит безопасности перевёл проект из состояния «работает» в «работает и проверяем»: CORS, секреты, Pydantic-валидация, экранирование XSS — закрыты; из 12 найденных в зависимостях уязвимостей исправлено 7, остальные задокументированы с планом. Обработка ошибок на обеих сторонах не даёт сбою внешнего сервиса уронить интерфейс, а следующие шаги (Telegram-алерты, ESLint, структурные логи) уже расставлены по приоритету.
